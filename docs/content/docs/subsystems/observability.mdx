Bastion records its metrics and spans through the Forge app it runs in, so they land wherever your app's already go: the `/_/metrics` scrape, and the OTLP endpoint Forge's tracing exports to. There's nothing to install. On top of that you get structured access logs and the stats the admin API and dashboard read.

## Prometheus metrics

Turn your app's metrics on and the gateway's come with them. Forge puts its namespace in front of every name, so they scrape as `forge_bastion_...`.

```go
bastion.WithMetrics(bastion.MetricsConfig{
    Enabled: true,
})
```

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `Enabled` | `bool` | `true` | Record the gateway's metrics |
| `Prefix` | `string` | `"gateway"` | Ignored. The names are fixed; the field is kept so existing config parses |

### Exported metrics

| Scraped name | Type | Labels |
|--------------|------|--------|
| `forge_bastion_upstream_request_duration_seconds` | Histogram | `protocol`, `status_class` |
| `forge_bastion_requests_rejected_total` | Counter | `reason` |
| `forge_bastion_retries_attempted_total` | Counter | `result` |
| `forge_bastion_circuit_breakers_transitioned_total` | Counter | `state` |
| `forge_bastion_upstream_targets` | Gauge | `health` |
| `forge_bastion_active_streams` | Gauge | `protocol` |
| `forge_bastion_background_job_duration_seconds` | Histogram | `job`, `result` |

`forge_bastion_upstream_request_duration_seconds` gets one observation per attempt to reach an upstream, retries included. It measures from sending the request to the upstream's response headers, or to the end of the handshake for WebSocket, so it tells you how slow the upstream is apart from the gateway. The buckets run from 5ms to 30s. Forge's own `http_server_request_duration_seconds` still measures the whole request as the client saw it.

`forge_bastion_upstream_targets` is set from a count of the monitored targets, on every registration, every health change and after each health check cycle. `forge_bastion_active_streams` counts the WebSocket, SSE and gRPC streams in flight, from the moment the gateway picks a target until the stream closes.

### Label values

Every label is a small fixed set. Route IDs, target IDs, URLs, hosts, paths and service names never become labels, because discovery creates those at runtime.

| Label | Values |
|-------|--------|
| `protocol` | `http`, `websocket`, `sse`, `grpc` (`active_streams` has the last three) |
| `status_class` | `1xx` to `5xx` for a response (a WebSocket handshake that succeeds is `1xx`), `error` when no response came back (dial, TLS, timeout), `canceled` when the client went away first |
| `reason` | `draining`, `ip_filtered`, `global_rate_limit`, `route_rate_limit`, `no_route`, `path_blocked`, `unauthenticated`, `hook`, `circuit_open`, `no_healthy_upstream` |
| `result` (retries) | `sent`, a retry that went out; `budget_exhausted`, a retry the policy wanted and the retry budget refused |
| `state` | `closed`, `open`, `half_open`: the state a breaker moved into |
| `health` | `healthy`, `unhealthy` |
| `job` | `discovery`, `openapi`, `asyncapi`, `health_check` |
| `result` (jobs) | `ok`, or `error` when the run, or at least one unit inside it (a service lookup, a spec fetch, a probe), failed |

### Queries

Upstream p99 by protocol:

```text
histogram_quantile(0.99, sum by (le, protocol) (rate(forge_bastion_upstream_request_duration_seconds_bucket[5m])))
```

Share of upstream attempts that got a 5xx or no answer:

```text
sum(rate(forge_bastion_upstream_request_duration_seconds_count{status_class=~"5xx|error"}[5m]))
  / sum(rate(forge_bastion_upstream_request_duration_seconds_count[5m]))
```

Breakers opening, and why requests are being turned away:

```text
sum(rate(forge_bastion_circuit_breakers_transitioned_total{state="open"}[5m]))
sum by (reason) (rate(forge_bastion_requests_rejected_total[5m]))
```

### Upgrading from the old metrics

Bastion used to declare its metrics under a configurable prefix with dotted names, and only two of them were ever recorded. Both put the target ID inside the metric name, one series family per upstream. They're gone. If a dashboard or alert scrapes them, move it:

| Old | Now |
|-----|-----|
| `gateway.circuit_breaker_state.<targetID>` | `forge_bastion_circuit_breakers_transitioned_total{state}`, and the per-target state in the admin API |
| `gateway.upstream_health.<targetID>` | `forge_bastion_upstream_targets{health}`, and per-target health in the admin API |
| `gateway.requests_total`, `gateway.request_duration_seconds` | Never recorded. Forge's HTTP server metrics, and `forge_bastion_upstream_request_duration_seconds` |
| `gateway.retry_total`, `gateway.rate_limited_total` | Never recorded. `forge_bastion_retries_attempted_total`, `forge_bastion_requests_rejected_total` |
| `gateway.active_connections.<protocol>` | Never recorded. `forge_bastion_active_streams{protocol}` |
| `gateway.cache_hits_total`, `gateway.cache_misses_total`, `gateway.discovery_routes.<source>` | Never recorded, and not replaced |

## Tracing

Forge starts a server span for every request, named after the route, so a proxied request shows up as `GET /*path`. Bastion adds the spans below. They use the instrumentation scope `github.com/xraph/bastion` and go to the tracer provider Forge installs, so sampling, propagators and the exporter are whatever your app's tracing config says.

| Span | Kind | Parent | Attributes |
|------|------|--------|------------|
| `proxy request` | Client | the server span | `bastion.route.id`, `bastion.route.path`, `bastion.route.source`, `bastion.protocol`, `bastion.proxy.attempt`, `http.request.method`, `url.scheme`, `server.address`, `server.port`, `http.response.status_code`, `error.type`, `rpc.system` and `rpc.grpc.status_code` for gRPC, `bastion.canceled` |
| `mirror request` | Client | none: a new trace, linked to the server span | the route attributes, method, scheme, host, port, status |
| `authenticate request` | Internal | the server span | `bastion.auth.result` (`ok` or `denied`), `bastion.auth.provider` |
| `call forward auth` | Client | `authenticate request` | method, scheme, host, port, status |
| `check upstream health` | Internal | none: one trace per cycle | `bastion.health.targets`, `bastion.health.failed`, `bastion.health.unhealthy` |
| `discover services` | Internal | none for a poll; the caller's span for the pass in Start or one an operator asks for | `bastion.discovery.services`, `bastion.discovery.unresolved`, `bastion.discovery.removed` |
| `fetch farp manifest` | Client | `discover services`, or the push request | method, scheme, host, port, status |
| `refresh openapi specs`, `refresh asyncapi specs` | Internal | none for the loops or a refresh started from a handler (linked to the request); the caller's span otherwise | `bastion.openapi.sources`, `.failed`, `.paths`; `bastion.asyncapi.sources`, `.failed`, `.channels` |
| `merge openapi specs`, `merge asyncapi specs` | Internal | the refresh | |
| `fetch openapi spec`, `fetch asyncapi spec` | Client | the refresh | method, scheme, host, port, status |
| `refresh jwks` | Internal | the caller for the first fetch, none after | `bastion.jwks.keys` |
| `fetch jwks` | Client | `refresh jwks` | method, scheme, host, port, status |

Every client span sends its trace context upstream, so the upstream joins the trace under the gateway's span instead of the client's. With tracing off, the client's own `traceparent` passes through untouched.

The server span gets the matched route's `bastion.route.*` attributes and `bastion.protocol`, and `bastion.reject.reason` when the gateway answers the request itself.

A retried request shows one `proxy request` span per attempt. An SSE span ends once the upstream answers and a WebSocket span once the handshake is done, so a stream that stays open for hours doesn't hold a span open with it. A gRPC span covers the whole call and ends with the last frame.

### What a span never carries

The path, the query string and the headers of the client's request, the auth subject and claims, and any error text. A span the gateway fails gets a short class (`transport error`, `timeout`, `503`, `grpc status 14`, `list services failed`) and an `exception` event that holds only the error's Go type. A 5xx from the upstream fails the `proxy request` span. A 4xx doesn't, since it's the upstream's answer to the client, and neither does a client that hangs up first: that sets `bastion.canceled` instead.

### Background work

The health monitor, the discovery poll, the spec refresh loops and the JWKS refresh run on the ctx Start was given, which carries Forge's boot span. Each loop drops that span where it begins, then starts a root span per unit of work, and only when there's work: an idle gateway doesn't mint a trace every tick. The dashboard broadcast and the rate-limiter cleanup get no spans.

### Tracing config

`bastion.TracingConfig` (`Enabled`, `PropagateFormat`, `SampleRate`) isn't read. Configure tracing on the Forge app instead; the fields stay so existing config parses.

## Structured Access Logging

### Configuration

```go
bastion.WithAccessLog(bastion.AccessLogConfig{
    Enabled:        true,
    RedactHeaders:  []string{"Authorization", "Cookie", "Set-Cookie"},
    IncludeBody:    false,
    MaxBodyLogSize: 4096,
})
```

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `Enabled` | `bool` | `true` | Enable or disable access logging |
| `RedactHeaders` | `[]string` | `["Authorization", "Cookie", "Set-Cookie"]` | Headers to redact in logs |
| `IncludeBody` | `bool` | `false` | Include request/response body in logs |
| `MaxBodyLogSize` | `int` | `4096` | Maximum body bytes to log |

### Log Fields

Every proxied request produces a structured log entry with these fields:

#### Request Fields

| Field | Description |
|-------|-------------|
| `method` | HTTP method (GET, POST, etc.) |
| `path` | Request path |
| `status` | HTTP response status code |
| `latency_ms` | Total request latency in milliseconds |
| `client_ip` | Client IP address (from X-Forwarded-For, X-Real-IP, or RemoteAddr) |
| `user_agent` | Client User-Agent header |
| `request_id` | Value of X-Request-ID header (if present) |
| `query` | Query string (truncated to 200 chars) |

#### Route Fields

| Field | Description |
|-------|-------------|
| `route_id` | Matched route ID |
| `route_path` | Route pattern |
| `route_protocol` | Route protocol (http, websocket, sse, grpc) |
| `route_source` | Route source (manual, farp, discovery) |

#### Upstream Fields

| Field | Description |
|-------|-------------|
| `upstream_url` | Selected target URL |
| `upstream_id` | Selected target ID |

#### Safe Headers

These headers are always included when present:

- `Accept`, `Content-Type`, `Content-Length`, `Referer`, `Origin`

Sensitive headers listed in `RedactHeaders` are logged as `[REDACTED]`.

### Log Levels

The access logger uses different log levels based on the response status code:

| Status Range | Log Level |
|-------------|-----------|
| 200-399 | `Info` |
| 400-499 | `Warn` |
| 500+ | `Error` |

### Admin Action Logging

Administrative actions (route creation, config changes, cache invalidation) are logged separately:

```json
{
    "msg": "gateway admin action",
    "action": "route_created",
    "resource": "route-abc123",
    "result": "success",
    "client_ip": "10.0.0.1",
    "user_agent": "curl/7.88.0"
}
```

## Gateway Stats

The proxy engine maintains an aggregated stats structure available via the admin API:

```go
type GatewayStats struct {
    TotalRequests    int64
    TotalErrors      int64
    ActiveConns      int64
    ActiveWSConns    int64
    ActiveSSEConns   int64
    AvgLatencyMs     float64
    P99LatencyMs     float64
    RequestsPerSec   float64
    CacheHits        int64
    CacheMisses      int64
    RateLimited      int64
    CircuitBreaks    int64
    RetryAttempts    int64
    RetryBudgetExhausted int64 // retries the retry budget refused
    TotalRoutes      int
    HealthyUpstreams int
    TotalUpstreams   int
    Uptime           int64
    StartedAt        time.Time
}
```

Access via the admin API:

```
GET /gateway/api/stats
```

### Per-Route Stats

Each route tracks its own metrics:

```go
type RouteStats struct {
    RouteID       string
    Path          string
    TotalRequests int64
    TotalErrors   int64
    AvgLatencyMs  float64
    P99LatencyMs  float64
    CacheHits     int64
    CacheMisses   int64
    RateLimited   int64
}
```

Per-route stats are included in `GatewayStats.RouteStats` keyed by route ID.

## Dashboard Integration

When the dashboard is enabled, all observability data feeds the real-time admin UI:

```go
bastion.WithDashboard(bastion.DashboardConfig{
    Enabled:  true,
    BasePath: "/gateway",
    Realtime: true,
})
```

The dashboard displays:

- Live request throughput and error rates
- Latency percentiles (p50, p95, p99)
- Active connections by protocol
- Upstream health status per target
- Circuit breaker states
- Cache hit/miss ratios
- Route-level traffic breakdown

## Audit Logging

Administrative actions are recorded as audit events:

```go
type AuditEvent struct {
    Action    AuditAction
    Resource  string
    Actor     string
    Timestamp time.Time
    Details   map[string]any
}
```

Supported audit actions:

| Action | Description |
|--------|-------------|
| `AuditRouteCreated` | A route was created |
| `AuditRouteUpdated` | A route was updated |
| `AuditRouteDeleted` | A route was deleted |
| `AuditRouteToggled` | A route was enabled/disabled |
| `AuditConfigChanged` | Gateway configuration was changed |
| `AuditDiscoveryForced` | Discovery refresh was manually triggered |
| `AuditCircuitReset` | A circuit breaker was manually reset |
| `AuditCacheCleared` | Cache was cleared |

Audit events can be consumed via the `AuditSink` interface for forwarding to external audit systems.
