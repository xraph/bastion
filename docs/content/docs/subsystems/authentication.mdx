Bastion provides gateway-level authentication that validates incoming requests before they reach upstream services. It supports multiple authentication strategies, per-route overrides, and integration with the Forge auth extension.

## Configuration

```go
bastion.WithAuth(bastion.AuthConfig{
    Enabled:        true,
    DefaultPolicy:  "deny",
    Providers:      []string{"api-keys", "jwt-tokens"},
    ForwardHeaders: true,
})
```

### Configuration Fields

| Field | Type | Default | Description |
|-------|------|---------|-------------|
| `Enabled` | `bool` | `false` | Enable or disable gateway authentication |
| `DefaultPolicy` | `string` | `""` | Default policy when no providers are configured (`"allow"` or `"deny"`) |
| `Providers` | `[]string` | `[]` | Ordered list of provider names to try (OR logic) |
| `ForwardHeaders` | `bool` | `true` | Forward authenticated identity to upstream via headers |

## Authentication Flow

When a request arrives and auth is enabled:

1. Check if the route has a per-route auth override. If `SkipAuth` is true, the request passes through.
2. Determine which providers to use (per-route providers override global providers).
3. Try each provider in order. If any provider returns a valid `AuthContext`, the request is authenticated.
4. If all providers fail, return 401 Unauthorized.
5. If the route requires specific scopes, verify the `AuthContext` has all required scopes. Return 403 Forbidden if not.
6. If `ForwardHeaders` is enabled, inject identity headers for the upstream.

## Built-in Providers

### API Key Authentication

Validates requests using API keys sent in a header or query parameter:

```go
apiKeyProvider := bastion.NewAPIKeyAuthProvider(
    "api-keys",       // Provider name
    "X-API-Key",      // Header to check (default: "X-API-Key")
    "api_key",        // Query param to check (optional)
    []*bastion.APIKeyEntry{
        {
            Key:     "sk_live_abc123",
            Subject: "service-a",
            Scopes:  []string{"read", "write"},
        },
        {
            Key:     "sk_live_def456",
            Subject: "service-b",
            Scopes:  []string{"read"},
        },
    },
)
```

The provider checks the header first, then falls back to the query parameter. Each key maps to a subject (identity) and optional scopes.

### Bearer Token Authentication

Validates Bearer tokens in the Authorization header using a custom validation function:

```go
bearerProvider := bastion.NewBearerTokenAuthProvider(
    "jwt-tokens",
    func(ctx context.Context, token string) (*bastion.GatewayAuthContext, error) {
        // Validate the token (e.g., verify JWT signature, check expiry)
        claims, err := validateJWT(token)
        if err != nil {
            return nil, err
        }
        return &bastion.GatewayAuthContext{
            Subject: claims.Subject,
            Scopes:  claims.Scopes,
            Claims:  map[string]any{"role": claims.Role},
        }, nil
    },
)
```

The provider extracts the token from the `Authorization: Bearer <token>` header and passes it to the validation function.

### Forward Auth

Delegates authentication to an external auth service. The gateway forwards selected headers to the auth endpoint and interprets the response:

```go
forwardAuthProvider := bastion.NewForwardAuthProvider(
    "external-auth",
    "https://auth.example.com/verify",
    []string{"Authorization", "Cookie", "X-Forwarded-For"},
)
```

Forward auth behavior:

1. The gateway sends a `GET` request to the auth endpoint.
2. Configured headers from the original request are forwarded.
3. `X-Original-URI` and `X-Original-Method` headers are added for context.
4. A `200` response means authenticated. The auth service returns identity info in response headers.
5. Any non-200 response means unauthenticated. The status code is forwarded to the client.

Response headers from the auth service that populate the `AuthContext`:

| Header | Maps To |
|--------|---------|
| `X-Auth-Subject` | `AuthContext.Subject` |
| `X-Auth-Role` | `AuthContext.Claims["role"]` |
| `X-Auth-Scopes` | `AuthContext.Scopes` (comma-separated) |

### JWT

Checks a Bearer JWT's signature against the keys in a JSON Web Key Set, then its `exp`, `nbf`, `iss` and `aud`:

```go
jwtProvider := security.NewJWTAuthProvider(security.JWTAuthConfig{
    Name:     "jwt-tokens",
    JWKSURL:  "https://idp.example.com/.well-known/jwks.json",
    Issuer:   "https://idp.example.com",
    Audience: "orders-api",
})
```

| Field | Default | Description |
|-------|---------|-------------|
| `JWKSURL` | | Where the provider loads its verification keys. Leave it empty and the provider accepts nothing |
| `Issuer` | | Expected `iss`, checked when set |
| `Audience` | | Expected `aud` (a string or one entry of an array), checked when set |
| `ScopesClaim` | `scope` | Claim the scopes come from, a space-separated string or an array |
| `SubjectClaim` | `sub` | Claim the subject comes from |
| `RefreshInterval` | `1h` | How often the JWKS is refetched |
| `Algorithms` | all six | Which of RS256, RS384, RS512, ES256, ES384 and ES512 the provider accepts |

You don't start anything yourself. The gateway starts the provider when it starts, or straight away if you register it once the gateway is running. On Forge's default boot path a `PhaseAfterRegister` hook runs after the extensions start, so registering there takes the second route. With `CentralMigrations` the hooks run before the extensions start, and the gateway's own start picks the provider up. Starting fetches the JWKS, then a refresh runs every `RefreshInterval` until the gateway stops. `StartKeyRefresh` still exists for code that calls it, and calling it on a running provider does nothing. A provider you use outside the gateway loads its keys on the first token it sees, and fetches again whenever they're older than `RefreshInterval`.

The provider rejects every token until it holds a verification key:

- A token whose `alg` isn't on the accepted list is rejected before any key is looked at. `none` and the HMAC algorithms are never on it.
- A token whose header lists `crit` parameters is rejected. The provider supports no header extensions (RFC 7515, section 4.1.11).
- If a fetch fails, the provider keeps the keys it has. A JWKS that comes back with no usable key counts as a failed fetch.
- If it has no key yet, the refresh retries after a few seconds and backs off toward `RefreshInterval`. A request that finds no key loaded starts a fetch too, at most once every five seconds, and waits up to three seconds for it.
- A token whose `kid` matches no loaded key makes the provider fetch again, inside the same five-second limit, so a key your identity provider has just rotated in is accepted without waiting for the next refresh.
- A token that names a `kid` is checked with the key carrying that `kid`. One that names none is checked with the single key that fits its algorithm, so a JWKS holding one key without a `kid` works, and it's rejected when several keys fit.
- A key is only used for its own algorithm family and curve: never an RSA key for an ES token, never a P-256 key for ES384, and never a key whose JWK `alg` names a different algorithm.
- ES signatures are read in the JWS form, R followed by S (RFC 7518, section 3.4).
- The JWKS fetch follows at most three redirects, and only to https URLs. When the gateway starts a provider whose `JWKSURL` is plain http to anything but loopback, it logs a warning.

A rejected client gets a 401 with `invalid token`, or `token expired` and `token not yet valid` for a verified token outside its time window. The specific reason is in the gateway's debug log.

## Registering Providers

Register auth providers on the gateway's auth handler and list their names in `AuthConfig.Providers`. The handler exists once the app has registered the gateway, so register them in a Forge lifecycle hook:

```go
err := app.RegisterHookFn(forge.PhaseAfterRegister, "bastion-auth", func(ctx context.Context, app forge.App) error {
    gw.Auth().RegisterProvider(apiKeyProvider)
    gw.Auth().RegisterProvider(bearerProvider)
    gw.Auth().RegisterProvider(jwtProvider)
    gw.Auth().RegisterProvider(forwardAuthProvider)
    return nil
})
```

## Per-Route Auth

Individual routes can override authentication settings:

```go
bastion.WithRoute(bastion.RouteConfig{
    Path: "/api/admin/*",
    Auth: &bastion.RouteAuthConfig{
        Enabled:   true,
        Providers: []string{"jwt-tokens"},
        Scopes:    []string{"admin"},
    },
    Targets: []bastion.TargetConfig{
        {URL: "http://admin-svc:8080"},
    },
})
```

### RouteAuthConfig Fields

| Field | Type | Description |
|-------|------|-------------|
| `Enabled` | `bool` | Enable auth for this route |
| `Providers` | `[]string` | Providers to use (overrides global list) |
| `Scopes` | `[]string` | Required scopes (all must be present) |
| `SkipAuth` | `bool` | Skip authentication entirely for this route |
| `ForwardAuth` | `bool` | Forward auth headers to upstream |

### Skipping Auth for Public Routes

```go
bastion.WithRoute(bastion.RouteConfig{
    Path: "/public/*",
    Auth: &bastion.RouteAuthConfig{
        SkipAuth: true,
    },
    Targets: []bastion.TargetConfig{
        {URL: "http://public-svc:8080"},
    },
})
```

## Auth Context

A successful authentication returns an `AuthContext`:

```go
type AuthContext struct {
    Subject      string         // Authenticated entity (user ID, service ID)
    Claims       map[string]any // Additional claims (role, email, etc.)
    Scopes       []string       // OAuth2 scopes or permissions
    ProviderName string         // Which provider authenticated this request
}
```

The `AuthContext` can be checked for scopes:

```go
authCtx.HasScope("admin")           // Check a single scope
authCtx.HasScopes("read", "write")  // Check all scopes (AND logic)
```

## Forwarded Headers

When `ForwardHeaders` is true and authentication succeeds, the gateway injects the following headers into the upstream request:

| Header | Value |
|--------|-------|
| `X-Auth-Subject` | The authenticated subject |
| `X-Auth-Provider` | The provider that authenticated the request |
| `X-Auth-Scopes` | Comma-separated scopes |
| `X-Auth-Role` | The `role` claim (if present) |
| `X-Auth-Email` | The `email` claim (if present) |

This allows upstream services to trust the gateway's authentication and extract identity information without re-validating credentials.

The gateway deletes these five headers from every incoming request before anything else runs. That holds on every route and every protocol, including routes that skip auth and gateways with `ForwardHeaders` off, so the copies an upstream sees were set by the gateway from an identity a provider accepted. Other `X-Auth-` headers, such as a token an API key provider reads, pass through.

## Integration with Forge Auth Extension

Bastion can integrate with the Forge auth extension's provider registry. When the Forge auth extension is loaded alongside Bastion, any providers registered in the Forge auth registry become available to the gateway:

```go
// Forge auth providers are automatically available
// e.g., if Forge auth has a "jwt" provider registered,
// the gateway can reference it by name
bastion.WithAuth(bastion.AuthConfig{
    Enabled:   true,
    Providers: []string{"jwt"}, // References Forge auth provider
})
```

The gateway checks its own local providers first, then falls back to the Forge auth registry.
